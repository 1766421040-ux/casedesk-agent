## 后端新增验证重点

- 模型主动选择允许工具、工具结果按对应 `tool_call_id` 回传、最终提案单独提交。
- 未知工具、越界订单、重复调用 ID、非法参数、轮次与工具预算、截断或超大响应均有测试。
- 不支持或失败的模型请求不会伪装降级为 demo；错误保存为可追踪的拒绝或失败。
- 政策更新时旧引用失效；再次检索使用新版本，旧工具结果保留在历史中。
- demo 非退款答复读取当前政策摘录，避免规则已更新而答复仍使用旧时效。
- 工单编辑冲突、运行/审批中编辑阻断、人工结案、拒绝后重开、重开保留账本和旧审批。
- 政策发布权限、退款正文保护、版本历史、工单/审计分页、真实日期窗口、旧库迁移和中断恢复。

具体输入和断言分别在 [`test_api.py`](../backend/tests/test_api.py)、[`test_agent_v2.py`](../backend/tests/test_agent_v2.py)、[`test_workflow_v2.py`](../backend/tests/test_workflow_v2.py)。

## 浏览器覆盖范围

[workflow.spec.ts](../frontend/tests/workflow.spec.ts) 的 10 项回归覆盖退款闭环与独立审批、拒绝与零退款、低证据/注入转人工、租户切换、可读失败、390px 布局、补资料/结案/重开、规则发布、编辑版本冲突、服务端分页搜索与会话失效。

[reliability.spec.ts](../frontend/tests/reliability.spec.ts) 的 3 项检查补充：

1. 旧租户的队列响应晚到，不覆盖新租户工作空间。
2. 运行工单 A 时切换到 B，A 返回后仍显示 B 的详情。
3. 首次队列请求失败，页面显示可恢复错误并可刷新恢复。

业务闭环使用真实本地 API。前两项竞态测试只延迟真实响应，不替换业务结果；失败 run 展示和首次队列 503 使用定向错误响应。它们验证 UI 错误处理，不作为真实供应商故障率的证据。

## 容器验证定义

CI 的容器任务包含 `docker compose build`、`up -d --wait`、[container-smoke.py](../scripts/container-smoke.py)、后端重启和 `--verify`。它会通过 Nginx 的公开本地端口验证静态页面与 `/api` 代理，创建物流工单并运行 Agent，重启后验证工单、run 和历史仍存在。构建成功与这些运行检查成功分别看对应步骤。

本机没有运行 Docker 容器；远程任务通过前不将容器启动或持久化写成已经验收。该任务也不验证云上高可用、生产流量或真实支付。

## 如何解释这些结果

**82 项 pytest、12 条 demo 场景和 13 项浏览器测试分别计数。** 真实模型工具协议使用 MockTransport / 测试替身，固定场景使用确定性 provider；没有使用真实供应商 API Key 测量任务成功率、引用语义正确率、费用或延迟分布。后续操作见 [真实模型评测清单](真实模型评测清单.md)。

数据库中的退款均为模拟记录。已有检查围绕声明的本地单 worker 架构，不作为多实例部署、真实支付或生产安全审计的结论。
