# 10 分钟演示：从工单到可复核的审批

本脚本使用离线 `demo`，不需要 API Key。目标是复现同一条业务链：生成提案 → 政策变化阻断旧审批 → 拒绝并补充资料 → 重新生成 → 独立批准 → 检查历史与租户范围。演示中的退款都只进入本地模拟账本。

## 准备一个新的演示数据集

先按 [README](../README.md) 安装依赖。若已有开发服务，先 Ctrl+C 停止。在仓库根目录启动本次独立演示：

```bash
export CASEDESK_DATABASE_PATH="$PWD/backend/data/walkthrough-$(date +%Y%m%d-%H%M%S).sqlite3"
CASEDESK_PROVIDER=demo CASEDESK_DEMO_SEED=true bash scripts/dev.sh
```

这会创建一个新数据库，不删除原来的 `casedesk.sqlite3`。使用新的数据库是为了让订单余额、预算、政策版本和签收时间都从一致的种子状态开始。只想返回日常数据时，停止服务后执行 `unset CASEDESK_DATABASE_PATH`，再用原启动命令运行。

打开 [本地工作台](http://127.0.0.1:5173)。所有账号的密码均为 `DemoPass!2026`。

| 身份 | 账号 | 本轮职责 |
|---|---|---|
| 极光数码客服 | `agent@aurora.demo` | 处理、重开和补充工单 |
| 极光数码审批主管 | `reviewer@aurora.demo` | 发布政策版本，独立批准 / 拒绝 |
| 海港生活客服 | `agent@harbor.demo` | 验证工作空间隔离 |

## 0:00–2:00：生成方案，看清楚哪些动作已发生

1. 登录极光数码客服，选择 **“耳机已签收，希望申请退款”**，订单应为 `AURORA-1001`，金额 ¥299。
2. 运行 Agent，分别查看处理方案、引用证据和执行轨迹。
3. 确认以下结果：工单待审批；方案金额 `29900` 分；引用属于 `aurora-refund:v1:*`；五个外层阶段完成。
4. 查看工具轨迹：正常退款路径包含初始检索、绑定订单查询和确定性方案提交；模型请求数应为 **0**，来源包含 `bootstrap` 与 `demo`。
5. 查看统计 / 审计，模拟退款总额仍为 **¥0**。此时只生成了提案，尚未批准。

讲解重点：离线演示证明工具边界、状态与界面能协作；真实模型是否正确选工具，需另做评测。

## 2:00–4:00：让旧证据失效，检查审批是否重新核验

1. 退出客服，使用极光数码审批主管登录。
2. 到知识库选择 **“退款与退货政策”**，查看版本 1。
3. 发布一个新版本：将标题改为 **“退款与退货政策 · 复核版”**；正文保持不变；发布原因填写 **“演示政策发布后旧提案需重新复核”**。
4. 查看版本历史，应同时保留 v1 和 v2。退款正文受保护，界面不能随意改变 30 天或金额条款。
5. 回到审批中心，尝试批准刚才的耳机退款方案，审批意见填写 **“核对订单与退款证据”**。
6. 应出现政策版本变化冲突，审批仍待处理，模拟账本仍是 **¥0**。旧方案中的 v1 证据应仍然可查看。

这里采用保守规则：即使只更改标题，只要文档版本变化，就要求重新核实。它牺牲了一些自动通过率，换取明确的审阅时点；没有实现语义等价版本自动放行。

## 4:00–6:00：保留旧记录，重新处理工单

1. 由主管拒绝该旧提案，原因填写 **“政策已发布 v2，请按新版本重新生成方案”**。工单应进入 `rejected`，账本不变。
2. 切回极光数码客服，打开原耳机工单，重新打开；理由填写 **“客户补充资料后按当前政策重新核实”**。
3. 编辑 / 补充资料，添加 **“客户确认商品未拆封，包装完好。”** 并保存。
4. 重新运行 Agent。工单再次待审批，新的 run 应引用 **v2** 政策。
5. 查看工单活动与历史运行：旧的 v1 提案和拒绝意见仍在，新增重开、修改与运行记录；新旧 run ID 不同。

版本冲突时刷新后重新核对；不要连续点击保存来覆盖他人刚完成的操作。已有待审批或运行中的工单会拒绝编辑。

## 6:00–8:00：独立批准，检查账本和回放

1. 切回极光数码主管，找到最新提案，核对 v2 引用、订单和 ¥299 金额。
2. 批准并填写 **“依据当前政策核对通过，同意模拟退款”**。
3. 确认审批 `approved`、工单 `resolved`、模拟退款总额 **¥299**；审计出现批准和模拟退款事件。
4. 再打开该工单历史与原审批，刷新页面。账本应仍为 ¥299，不应再次增加。

页面刷新证明读取历史不会再次执行；同幂等键并发重试、事务回滚与预算竞争由自动化测试专门验证，不能仅凭这一步点击宣称全部通过。

## 8:00–10:00：验证普通咨询与租户范围

1. 客服登录，选择 **“查询智能手表配送进度”** 并运行。应得到引用当前物流政策的答复，无新退款审批。可以填写结案理由 **“已向客户说明当前配送规则，待物流进一步确认”** 后人工结案。
2. 运行 **“咨询国际运费与关税”**，应因缺乏证据转人工；没有退款提案。
3. 切换海港生活客服。此空间有自己的种子工单、规则与订单，极光数码的退款、政策 v2 和工单修改不可见；模拟账本仍为 ¥0。

界面隔离是这一步的观察范围；直接伪造跨租户 ID 的请求检查见后端自动化测试。

可保留工作台、政策历史、工具轨迹和审批后审计四张截图。不要在演示记录中写真实支付到账、模型准确率或节省人力数字。

## 常见偏差

- **订单已经退过款 / 政策不是 v1：** 没有使用本脚本的新数据库；先确认当前启动终端里的路径，再新建演示数据集。
- **旧审批无法编辑 / 重新批准：** 已决定的审批保持原记录；重开工单后生成新提案。
- **重新打开仍不能退款：** 重开不重置订单余额和预算；已退款的金额不能再退。
- **没有模型工具循环：** demo 是确定性规则；要看模型主动补查，按 [后端说明](../backend/README.md) 接入真实工具模型，并使用 [评测清单](真实模型评测清单.md) 记录结果。
- **测试要重复运行：** pytest、场景评估与 E2E 使用各自临时数据库，命令见根 README，不要直接改正在演示的数据来制造异常。
