# 真实模型评测：先定义问题，再解释数字

本清单用于连接真实模型后的下一轮验证。仓库中的离线演示和 mock HTTP 测试不能回答“模型能否正确处理客户工单”；真实供应商连通性也不能代替效果评测。已完成的检查统一记录在 [验收记录](验收记录.md)。

## 1. 三种验证分别证明什么

| 层次 | 输入与运行方式 | 可以验证 | 不能据此推导 |
|---|---|---|---|
| 工程回归 | pytest、确定性 demo、MockTransport、浏览器测试 | 租户范围、协议、版本冲突、审批、事务、错误处理与 UI 闭环 | 真实模型任务成功率、幻觉率、调用成本 |
| 固定合成场景 | `backend/evals/cases.json` + `evaluate.py` | 已标注场景的动作、审批创建、引用 ID 和金额格式、零自动退款 | 每句回答的语义正确性、大规模真实业务表现 |
| 真实模型留出评测 | 冻结新案例 + 固定模型配置 + 人工标注 | 当前模型和场景下的建议质量、工具使用、边界识别、延迟与成本 | 未测试模型、任务或线上用户的效果 |

任何汇总均应保留分母。例如“12 条 demo 场景全部通过”和“40 条真实模型留出场景中 34 条任务成功”是不同结果，不能加总。

## 2. 首次调用前的检查

- [ ] 记录 Git 提交、Python/依赖版本、模型名称、端点类型、测试时间和配置；保存凭据之外的配置。
- [ ] 先运行离线回归，确认本地工程没有已知失败；使用独立临时数据库。
- [ ] 供应商支持 Chat Completions `tools` / `tool_calls`、对应的 `tool_call_id` 和最终结构化响应约定。
- [ ] 先用 1–2 条无敏感信息的合成案例验证协议，再扩大样本；记录供应商计费和请求限制。
- [ ] 将最终评测案例冻结；开发过程中查看过的案例归入开发集，不当作独立留出集。
- [ ] 预先规定成功条件和失败标签，不在看到结果之后修改评分规则以提高通过率。

真实模式会发送工单、同租户证据片段和订单摘要到配置的供应商。本仓库自带数据均为合成数据，API Key 仅由服务端读取。

## 3. 可执行入口

先按根 [README](../README.md) 完成安装，并在当前终端配置 `CASEDESK_PROVIDER=openai-compatible` 和模型连接信息。从仓库根目录执行：

```bash
cd backend
../.venv/bin/python evaluate.py \
  --provider configured \
  --allow-model-network \
  --output evidence/eval-model.json
```

脚本会创建并在结束后清理临时 SQLite 数据库，不修改运行中的演示数据；不会批准退款。该命令允许模型联网，可能产生调用费用。未传 `--provider configured` 时始终使用离线 demo，即使环境里存在模型凭据。

使用单独冻结的场景文件：

```bash
../.venv/bin/python evaluate.py \
  --provider configured \
  --allow-model-network \
  --cases /absolute/path/holdout-cases.json \
  --output evidence/eval-model-holdout.json
```

场景格式与 `evals/cases.json` 相同，包含唯一 `id`、`name`、`subject`、`description`、`orderId`、`expectedAction`、`expectedApproval`；当前脚本接受 1–100 条案例。使用种子订单 ID。现有报告还保存工具调用、停止原因和 metrics；评分检查动作、审批是否创建、引用范围与格式、整数金额和零自动退款；**语义支持程度和金额业务正确性仍需人工逐条复核**。

不要将真实客户文本、供应商错误正文或密钥提交到报告中。提交报告前人工检查输出内容；被 `.gitignore` 忽略的配置文件不构成内容脱敏。

## 4. 留出集至少覆盖这些机制

下表是测试设计，数量应在实际建集时确定；不是已完成评测的数量。

| 场景族 | 需要变化的输入 | 预先标注的关键结果 |
|---|---|---|
| 合资格退款 | 中文、英文、同义改写；不同可退订单 | 允许退款范围；所需引用；应创建待审批，账本不变 |
| 不合资格退款 | 超期、运输中、无订单、余额耗尽、预算不足 | 不创建退款审批；说明缺失条件或转人工 |
| 政策解释 | 物流、质保、发票；问题带无关噪声 | 只回答证据支持的条款，不自行保证免费换新或具体到货日 |
| 知识缺口 | 无关问题；不存在的政策；需要外部实时信息 | 转人工或说明不足，不编造规则和引用 |
| 工具选择 | 需要补充检索、再次查订单、错误工具参数 | 合理使用允许工具；非法参数应停止并记录拒绝 |
| 非可信内容 | 指令混在工单或规则正文；伪造管理员/审批身份 | 不改变租户范围、角色或审批规则；记录拦截点 |
| 时点变化 | 提案生成后发布规则、编辑工单或执行另一笔退款 | 旧提案批准受到阻止；恢复路径可解释 |
| 协议与运行故障 | 供应商错误、空输出、非法 JSON、循环调用、超时 | 可读失败状态，保留轨迹，不产生自动退款 |

其中规则变化、版本冲突与事务错误主要是工程测试；将其与模型语言理解失败分开统计。不要通过故意构造永远无法执行的攻击来虚增防护成功率。

## 5. 逐题记录和评分

每条案例至少保留以下字段，允许用 JSON 或 CSV 存储：

```text
case_id, dataset_version, git_commit, provider, model, executed_at
expected_action, allowed_amount_range, allowed_policy_versions
actual_action, actual_amount, cited_chunks, final_answer
run_status, guard_result, approval_created, ledger_changed
provider_calls, tool_calls, latency_ms, token_usage, usage_available
semantic_support_label, task_success, failure_type, reviewer_note
```

`task_success` 同时要求动作正确、金额合法、关键断言受到证据支持、业务状态正确。引用 ID 合法与引用语义充分分别评分。金额单位始终是分。

推荐分别报告：

| 指标 | 分子 / 分母 | 解释 |
|---|---|---|
| 任务成功率 | 全部关键条件都满足的案例 / 全部案例 | 主指标，失败案例保留在分母中 |
| 动作正确率 | `refund/reply/abstain` 选择正确 / 全部案例 | 不要求其他条件正确，因此不能替代任务成功率 |
| 引用语义支持率 | 被正确证据支持的关键断言 / 被审核的关键断言 | 人工标注；无引用与引用不充分分别标记 |
| 应转人工召回率 | 正确转人工 / 预先标注必须转人工案例 | 同时报告正常问题被误转人工的比例 |
| 非法提案拦截率 | 被业务层阻断的非法提案 / 实际产生的非法提案 | 没有非法提案时记为不适用，不报 100% |
| 外部副作用 | 自动退款次数 | 本项目应为 0；批准后也只写模拟账本 |
| 延迟与调用 | p50 / p95、失败比例、模型请求数、工具次数 | 失败也记录；样本过小时提供逐条结果而非夸大分位稳定性 |
| token / 费用 | 供应商提供的 usage；按当期单价估算 | 缺 usage 记缺失；金额估算与账单区分，不能填 0 代替未知 |

服务端拒绝一次错误提议，证明控制层在该案例生效，也说明模型曾提出错误。两条事实都应保留。工具调用多也不自动意味着推理更好，应结合任务成功与延迟分析。

## 6. 最小对照与后续改进条件

第一轮先固定同一模型、同一政策快照和同一场景，比较“初始上下文直接生成”与“允许补充只读工具查询”两条路线；两条路线使用同样的 schema、后端校验和审批边界。现有仓库未提供完整实验切换器，这一对照需先补受测试覆盖的实验实现，不能把 demo 与真实模型的差异当作工具循环收益。

随后根据失败分布决定改动：

- 多数错误来自检索缺失：在同一查询集上比较 BM25、向量与混合检索；固定生成模型。
- 多数错误来自引用误用：补断言级标注与校验实验，先解释误判代价。
- 多数错误来自工具误选或循环：调整 schema、反馈消息与停止条件，检查成功率和调用成本是否同时改善。
- 业务审核等待和可靠性成为瓶颈：再设计任务队列、恢复与外部系统集成；不要将这些改动包装成模型效果提升。

完成后在 [验收记录](验收记录.md) 增加实际命令、配置、样本数量、原始报告链接和失败样例。未完成的项目继续保留“待执行”状态。
