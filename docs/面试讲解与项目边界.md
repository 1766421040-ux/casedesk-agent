# CaseDesk：面试讲解与源码路线

面向 Agent / 大模型应用岗位，用“业务问题 → 模型能做的动作 → 服务端控制 → 可复核证据”组织介绍。以下材料对应当前仓库；简历中应只保留自己能运行、解释并修改的部分。开发使用 AI 辅助，上游和仓库实现范围见 [UPSTREAM](../UPSTREAM.md)。

## 1. 90 秒讲解

> 我做的是售后工单处理系统。客户提出退款或物流问题时，模型需要查政策、查订单并提出方案，但它不应该直接决定付款。
>
> 我用 LangGraph 组织五个业务阶段，在方案生成阶段加入有次数和时间预算的模型工具循环。工具只有检索当前租户规则、查询工单绑定订单、提交结构化方案；身份与权限来自服务端。工具参数、结果、拒绝原因和模型调用次数都会记录。
>
> 退款提案需要另一位 reviewer 审批。批准时在事务内重新检查政策版本、签收日期、订单余额与租户预算，再一起写模拟账本、状态和审计。工单可以编辑、结案和重开，使用版本号防止旧页面覆盖新内容，历史提案和审批保留。
>
> 目前有不需要 Key 的确定性演示，以及经过 mock 协议测试的真实模型接入。工程验收和真实模型质量分开记录；支付仍是本地模拟，真实模型效果评测是下一步。

讲完立即展示一张工单和一次政策版本冲突。比逐个列框架名称更容易让面试官判断你理解了什么。

## 2. 三个核心问题及证明材料

| 核心问题 | 设计回答 | 现场证据 |
|---|---|---|
| 模型为什么不会获得付款权限？ | 工具 allowlist 不包含付款；租户、订单范围、schema 和审批由后端决定 | 工具定义、越界订单拒绝测试、客服审批 403 |
| 等人审批时，依据和余额变了怎么办？ | 引用保留版本；批准在写事务中读取最新订单、预算和政策版本 | v1 提案在 v2 发布后被拒绝执行，重新生成才可批准 |
| 用户反复点击、工单重新处理会怎样？ | 请求幂等、唯一约束、事务、版本冲突检查；重开保留历史和已退款金额 | 同 key 回放、并发审批测试、重开后余额不重置 |

适合现场展示的完整链路见 [10 分钟演示](十分钟演示.md)。真实模型工具调用的协议测试见 [`test_agent_v2.py`](../backend/tests/test_agent_v2.py)，不要把 demo 的固定工具顺序讲成模型自主推理的证据。

## 3. 按岗位调整重点

| 投递方向 | 介绍主线 | 值得展开的实现 |
|---|---|---|
| Agent / 大模型应用 | 不确定的模型建议如何进入可控业务流程 | 工具 schema、消息循环、调用 ID、预算、证据、终止原因和评测 |
| Python 后端 | 多租户状态与金额一致性 | 会话、租户范围、乐观锁、事务、幂等、并发和迁移 |
| AI 全栈 | 用户能处理异常并完成闭环 | 角色视图、证据对照、失败提示、版本历史、重开和响应式界面 |

这是一个项目的不同切面，不应把同一仓库包装成三个互不相关的工作经历。主投 Agent 岗时，先讲模型的决策范围和失败控制，再补后端和界面。

## 4. 可据实使用的简历候选文案

- 基于 LangGraph、FastAPI 和 React / TypeScript 构建售后工单 Agent，在固定业务阶段内实现受控工具循环，支持租户内政策检索、绑定订单查询与结构化方案提交，并记录调用来源、停止原因和供应商 token usage。
- 设计版本化工单与政策发布流程，使用乐观锁处理并发编辑，保留历史证据；退款方案经独立审批，在 SQLite 事务中复核签收窗口、订单余额、租户预算与政策版本，结合幂等键处理重复请求。
- 完成离线场景、工具协议、权限、并发审批和浏览器闭环回归，交付可运行工作台、容器配置与复现文档；工程结果和真实模型质量分层评估。

若需要量化，引用 [验收记录](验收记录.md) 中当前提交实际通过的检查，不添加未测的效率、准确率、日处理量或吞吐数字。若个人主要工作是理解和改造初版，可明确写“基于初版完成……改造与验证”，并指出自己的提交。

## 5. 高频追问

### “这个项目中的 Agent 到底在哪里？”

外层五个阶段保证必要的初始检索、查单和校验。真实模型在 `draft` 中可以选择允许工具、追加查询、利用工具返回结果再决定下一步，最终提交方案。循环受最大请求数、工具数和时间预算约束。它是单模型的业务工具循环，不是多 Agent、任意代码执行或开放环境自主规划。

### “有了模型工具调用，为什么还先检索和查单？”

当前场景中这两项是最低业务上下文，固定获取能减少遗漏；模型只在必要时补查。代价是简单问题也可能承担固定查询成本。是否让模型从零选择工具，应在同一模型、数据与校验条件下对照评测，而不是预先宣称自主程度越高越好。

### “为什么不用向量数据库？”

合成政策库小、条款与意图清楚，BM25 是可复现的起点。当前还有意图类别筛选和退款条款补齐，不能把结果全归功于 BM25。新增向量检索前，应冻结同义改写、跨语言和长文档查询集，比较证据召回和最终任务成功，再衡量依赖与延迟成本。

### “工具 schema 就能保证安全吗？”

schema 只约束结构。还要限制工具名称、服务端身份、订单范围、金额、引用和政策时点。`lookup_order` 连同租户内的其他订单也不允许查询；`submit_proposal` 不负责付款。提示词只能提供指导，关键词注入检测也只是补充，不是权限根基。

### “为什么 JSON 和工具调用两种终止方式都支持？”

部分兼容模型会返回最终 JSON。服务端把它送入同一个 `submit_proposal` 执行边界，使用同样的结构与业务校验，轨迹中明确标为 `final_response`。HTTP 失败不会退回 demo；不支持工具请求的服务仍会失败，不用“兼容”掩盖协议差异。

### “有引用就代表回答正确吗？”

不代表。当前校验引用 ID 是否属于已获取证据、是否与方案声明一致、版本是否仍然有效；没有逐句判断证据是否支持断言。需要人工标注引用语义支持程度。模型生成非法提议被拦住，应同时记为模型错误和控制层成功，不能合并成一个高准确率。

### “为什么审批不使用 LangGraph interrupt？”

当前图处理的是方案生成，审批是独立持久化业务对象。这样可以直接用 API、会话身份与数据库事务处理人工决定。实现没有 checkpointer 或图节点续跑；不能将历史读取说成断点恢复。

### “只修改政策标题，为什么也会拦住旧审批？”

当前失效依据是文档版本，保守而可解释。标题变化也改变版本，因此需要重新核实。未来若希望只对业务含义变化失效，需要区分语义版本与展示版本，并为放行逻辑设计测试；当前没有该机制。

### “重开已退款工单会再次退钱吗？”

重开只把工单恢复为可处理状态，不清空订单累计退款或旧审批。新运行按最新余额重新计算上限；已全额退款的订单不会再形成同金额审批。即使两张工单争用同一订单，也在批准事务中重新检查。

### “幂等是不是 exactly-once？”

这里是当前数据库事务内的重复处理约束：同 key 同请求回放，异参冲突，账本对审批还有唯一约束。它不是外部支付、数据库与消息系统之间的分布式 exactly-once；接真实支付需要另做回调、补偿与对账。

### “进程重启、多 worker 和超时怎么处理？”

重启保留已保存结果，将遗留的运行、节点与工具标为失败，不自动续跑。当前仅一个 worker；多个 worker 启动可能把彼此任务误判为遗留。时间预算在 HTTP 和循环边界检查，不是强制终止线程；记录实际耗时，而不承诺硬实时截止。

### “接下来最值得做什么？”

先完成真实模型留出评测，分别记录动作、金额、引用语义、转人工判断、工具使用和成本。若主要失败是检索缺失，改检索；若是工具误用，改 schema、反馈与停止策略。线上部署能力则另做任务队列、身份生命周期和外部副作用设计，不用增加框架数量替代问题证据。

在正式面试前，亲自完成：复现 10 分钟链路；解释一个并发失败测试；为一个新业务问题补案例；追踪一次真实模型错误并补评测记录。把实际修改与理解沉淀成可检查的提交，比背诵一组框架名称更有说服力。
