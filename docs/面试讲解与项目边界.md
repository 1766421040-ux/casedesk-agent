# CaseDesk：面试讲解与项目边界

基于当前仓库源码整理，2026-10-26。定位为可运行、可检查的 **Agent 工程作品**，主投 Agent / 大模型应用，兼顾 Python 后端和 AI 全栈。测试结果应引用实际验收记录；本文不填写未经执行的通过数或效果指标。

## 1. 先用一分钟讲清楚

> CaseDesk 是一个企业售后工单工作台。我把任务范围限定在退款、物流、质保和发票咨询：先识别业务意图，检索本租户政策，再读取本租户订单，生成有引用的处理方案。流程由 LangGraph 编排。模型只能提出退款、回复或转人工建议；服务端校验证据与金额，退款方案必须由另一名审批人确认后才写入本地模拟账本。工单、引用版本、节点轨迹、审批和账本都保存在 SQLite 中，React 界面可以逐步检查。当前重点是受控业务执行的工程闭环；默认模式是确定性演示，真实模型接口已经实现，但模型效果仍需要独立评测。

这段话描述的是代码能力。面试中“我负责”“我设计”的范围，必须与自己实际理解、修改、调试和验证的部分一致。项目使用 AI 辅助开发时，可以坦率说明，并用源码讲解、问题定位和自己的改动证明能力。

## 5. 与普通问答型 RAG 演示的可验证差异

这里比较的是“检索资料后生成回答”的最小问答原型，不是断言所有现有 RAG 系统都缺少这些能力。CaseDesk 的差异目前是可检查的工程机制，没有通过对照评测证明其总体效果更好。

| 维度 | CaseDesk 中可以检查的差异 | 如何验证 | 仍然缺什么 |
|---|---|---|---|
| 从回答到业务状态 | 退款提议创建审批记录，审批后才改变订单与账本 | 运行后账本仍为零；独立批准后出现模拟账本记录 | 真实业务集成、外部支付回调与对账 |
| 模型与权限分离 | 模型不能设定租户或绕过审批，服务端检查动作/金额/引用 | 注入伪造金额、外租户引用，检查无审批/无退款；客服直接审批得到拒绝 | 更丰富的攻击集、独立安全评审 |
| 引用与业务时点 | 保留文档版本，并在批准时复核当前版本 | 在隔离测试中变更政策版本，审批应拒绝过期方案 | 文档编辑、重建索引、发布与迁移流程 |
| 执行可检查 | 保存各节点输入摘要、输出、开始/结束时间和失败状态 | 获取历史 run，确认只读，不新增账本或审计动作 | 标准化可观测性、脱敏策略、保留期限、分布式追踪 |
| 重复/并发约束 | 运行和审批有幂等处理，账本唯一约束和事务内再校验 | 同 key 重放、不同审批争用订单/预算的集成测试 | 多实例、消息重复投递、外部副作用一致性 |

**下一项最有价值的补充是实际模型评测。** 固定一份从未用于调提示词的合成留出集，记录模型名称、配置和运行时间，逐题标注预期动作、允许引用和允许金额。分别统计提议正确性、引用是否支持回答、应转人工的识别、越权尝试是否被业务控制阻断、延迟、费用及失败原因。模型答对与服务端拦住错误是两种指标，必须分开。当前代码没有自动收集完整 token/费用评测流水，不能预先声称已经具备。

## 6. 十个面试追问与回答要点

### 1. 为什么叫 Agent，为什么还用固定流程？

它是受业务约束的 Agent 应用：围绕工单取得政策与订单上下文，生成动作提议，再交给确定性控制与人工审批。当前只有五个固定节点，真实模型主要在 `draft` 节点参与，没有自主选择工具、反复规划或多 Agent 协作。固定流程让当前范围的约束更容易检查；是否增加动态分支应由新的业务任务决定。

### 2. 为什么用 BM25，而没有向量数据库？

当前合成知识库很小，政策词汇明确，BM25 提供可复现、无需 embedding 服务的检索基线。实现同时使用意图筛选，因此不能将表现全部归因于 BM25。若扩展到同义改写、多语言或大量资料，应在同一留出查询集上比较词法、向量和混合检索，而不是先假定新组件更好。

### 3. 模型到底能做什么，能不能直接调用退款？

模型返回 `answer` 和 `proposal`，动作仅允许 `refund/reply/abstain`。订单查询由固定 Python 节点完成；模型没有付款工具，也不拥有审批权限。退款提议经过 schema 和策略校验后只创建待审批记录，真正的本地账本变更在独立审批 API 中完成。

### 4. 人工审批是不是 LangGraph interrupt？

不是。Graph 运行结束并保存结果，数据库创建 `pending` 审批；随后 reviewer 通过另一个 HTTP 请求决策。没有 checkpointer 或 `interrupt`，所以“运行 completed、工单 awaiting_approval”是正常组合，不能把这套实现描述为 Graph 暂停/恢复。

### 5. 多租户是怎么隔离的？

身份来自服务器验证的会话，租户从用户记录派生，业务 API 不接受客户端覆盖租户。工单、订单、知识、run、审批和审计查询都限制租户；跨租户资源返回不存在。当前是应用层共享 SQLite 表的逻辑隔离，不能称为数据库原生行级安全或物理隔离。

### 6. 幂等键和 exactly-once 有什么区别？

同租户的运行 key 绑定工单与申请人；审批 key 绑定审批对象、决定、理由和执行人。相同请求返回保存结果，不同参数复用 key 返回冲突；账本对审批 ID 还有唯一约束。它保证的是当前本地事务边界内的重复处理约束，不能推导出真实支付或分布式端到端 exactly-once。

### 7. 为什么批准时还要重新检查预算？

生成方案与人批准之间可能有其他审批消耗同一订单余额或租户预算。`BEGIN IMMEDIATE` 在写事务内读取最新状态，检查订单资格、余额、上限、预算与政策版本，再一起写入订单、账本、审批、幂等响应和审计，避免仅凭生成时快照执行。这正是本项目后端价值的重点。

### 8. 有引用就能保证回答真实、没有提示注入吗？

不能。代码校验引用 ID 属于当前检索结果，并检查回答中包含相应引用标记；没有逐句判定引用是否支持自然语言断言。注入关键词只是辅助检测，权限依靠服务端约束；模型仍可能给出措辞错误或未被语义验证的回答，需要真实模型评测和人工复核。

### 9. 服务重启后会自动继续吗？为什么只能单 worker？

已经保存的记录可以读取；启动时把遗留的 `running` 记录标为失败，用户使用新运行键重试。没有从失败节点续跑，多 worker 启动可能把其他进程的活动任务误判为遗留任务，因此当前明确只部署一个 worker。SQLite WAL 和线程内并发测试不等于支持多实例调度。

### 10. 如何证明项目有效？现在最大的缺口是什么？

先通过可复现的接口与浏览器验收证明业务约束，再用固定真实模型评测集证明建议质量。当前自动化测试包括确定性 provider、恶意输出替身以及 mock HTTP 模型端点，能证明若干工程行为；不能证明某个真实模型的成功率、成本或泛化能力。最大的缺口是实际模型与更丰富真实任务的评估，以及生产部署所需的外部业务集成和运行治理。
